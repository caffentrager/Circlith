# Circlith UI/UX 독립 비판 감사

- 감사일: 2026-10-19
- 대상: `codex/ui-workspace-refresh` 작업 트리 (HEAD `982bf5c` + **미커밋** UI 개편). Vite dev 서버(`:5173`, simulation 모드)에서 실행.
- 공개 Pages(`caffentrager.github.io/Circlith/`, `/simulation/`)는 `build-info.json` 기준 HEAD `982bf5c` 빌드이며 **개편 전 레이아웃**(좌 190px / 우 230px aside, Inspector 없음)이다. 사용자가 말한 구성(Inspector·Committed edits·상태바)은 미커밋 작업 트리에만 있다.
- 코드는 수정하지 않았다. 측정 스크립트는 scratchpad에만 두었다.

## 0. 증거 등급과 한계

| 표기 | 의미 |
|---|---|
| **[실측]** | Playwright(Chromium)로 작업 트리를 실행해 측정/재현 |
| **[코드]** | 소스·CSS를 읽고 확인 |
| **[추정]** | 전문가 휴리스틱. 사용성 테스트 아님 |

한계(숨기지 않는다):
1. 프롬프트에 스크린샷이 첨부되지 않았다. 설명된 구성과 일치하는 작업 트리를 1440×900에서 직접 캡처해 대체했다. XOR 선택 상태는 직접 재현했다.
2. 실제 Windows IME, 스크린리더, 터치, 사람 대상 테스트는 하지 못했다. 코드에서 `isComposing` 가드는 확인했으나 동작은 **미검증**.
3. 경쟁 제품 비교는 제품 지식 기반이다. 이번 세션에서 공식 문서를 다시 열람하지 않았다.
4. editor 모드 별도 실행은 하지 않았다. 같은 소스에서 `simulationAvailable` 플래그만 다르다([코드] `src/config/app-mode.ts`).
5. 100개 부품 fixture는 **배선 없이** 부품만 배치했다. 대형 배선 성능은 측정하지 못했다.
6. 점수는 전문가 휴리스틱 추정치다.

## A. Executive Verdict

**질문: 실제로 쓸 만한 회로 CAD인가, CAD 외형만 흉내 낸 프로토타입인가?**

판정: **"외형은 CAD 셸, 내부 UX는 프로토타입 단계."** 셸(헤더/좌우 패널/상태바)은 CAD 형태를 갖췄고 구조가 깨지는 곳은 없다(1440→390px에서 가로 넘침 0건 [실측]). 그러나 (1) 배선의 전기적 의미가 화면에서 틀리게 읽히는 사례가 재현되고, (2) 저장이 없으며, (3) Inspector가 개발 중 쌓인 명령 버튼의 적재소로 남아 있다. 교육용 논리 시뮬레이터로서 "첫 5분 데모"는 가능하지만 반복 작업 도구로는 아직 아니다.

### 핵심 문제 5개

1. **서로 다른 연결망이 같은 선분 위에 겹쳐 그려진다 (Critical, 재현됨).** Input1→AND2와 Input2→AND1이 `x=450`에서 y 210~390 구간을 공유한다. 시뮬레이션에서 한 선 위에 `1`(초록 실선)과 `X`(빨강 점선)가 번갈아 보인다. 진단은 0개다. 가장 흔한 2입력×2게이트 회로에서 발생한다.
2. **회로가 저장되지 않는다 (Critical).** `localStorage`는 설정 3종만 쓴다. 회로 저장·불러오기·`beforeunload` 경고가 없다. 알림은 10px 회색 "메모리에서 편집 중"뿐이고, 입력 가능한 프로젝트 이름은 어디에도 저장되지 않는다.
3. **Inspector가 4~5개 역할을 섞는다 (High).** 선택 객체 속성, 전역 배선 설정 카드, 선택 요약·삭제, 전역 통계, 명령 버튼 6개, 디버그 문구(`초안: NONE / 도구: SELECT`), 시뮬레이션 패널이 한 스크롤 열에 있다. 시뮬레이션을 켜면 **출력값이 900px 높이에서 접힘선 아래로 밀린다.**
4. **글자가 작다 (High).** 보이는 문자의 **71%가 11px 이하**, 24%가 10px 이하다. 도면 안 핀 라벨은 7px, Input/Output 값은 6px(100% 줌)이다. 반면 속성 모달은 13~16px라 같은 앱에서 크기 체계가 둘이다.
5. **같은 객체에 이름이 세 가지, 같은 정보가 3중 노출 (Medium-High).** 한 AND가 캔버스에서 `AND2`, 도면 트리에서 `AND 1`, Inspector에서 `AND`이다. 선택 수는 3곳, Logic ON/OFF도 3곳, 도구 이름도 3곳에 중복된다. 화면 공간은 줄고 인지 부하는 는다.

### 두 가지 핵심 질문

**Q1. 가장 많은 공간을 차지하면서 사용자 가치가 낮은 요소는?**
- **Inspector 하단 절반 (292px × 약 480px).** 연결 유지 이동·반시계/시계 회전·취소·꺾임 전환·경유점 제거 버튼, 배선 설정 카드, 디버그 문구. 대부분 단축키(`R`, `Esc`, `Shift+Space`, `Backspace`)와 중복된다. 선택이 없을 때는 이 버튼 대부분이 `opacity .45`로 비어 보이는 상자가 된다.
- 그다음은 좌측 "조작 안내" 블록(5줄 + 체크박스 + 개발자 메모). 개발자 메모 "Safe Move 경로는 잠정 규칙입니다. 회로 저장은 후속 단계입니다."가 사용자에게 그대로 노출된다 [코드 `App.tsx:784`].
- 36px 보조 툴바 한 줄도 가치가 낮다. 정적 라벨 "도면 01", 패널 토글 두 개, 줌 컨트롤이 들어 있다.

**Q2. 사용성을 가장 크게 올릴 변화는, 왜 아직 안 됐나?**
- 1순위: **연결망 인식(net-awareness).** 객체/배선 선택 시 같은 연결망 전체 강조, 서로 다른 연결망의 겹침을 진단으로 검출, 라우팅 시 레인 분리. 이 제품의 핵심 질문은 "무엇이 무엇에 연결됐는가"다.
- 2순위: **Inspector를 객체 전용으로 줄이고 이름·입력 수·반전을 직접 편집**하며, 시뮬레이션 결과는 별도 고정 영역으로 분리.
- 아직 안 된 이유 [코드 근거]: 개편이 **셸 재도장**이었기 때문이다. 이번 diff는 CSS와 새 래퍼 컴포넌트 중심이다. `App.tsx:1229–1291`의 기존 aside 명령 버튼은 그대로 남았고, `workspace.css`가 `.properties > h2`, `.properties > button` 같은 직계 자식 선택자로 덧칠한다. 기능 누적(QA 수정마다 버튼 추가)을 정보 구조 재설계 없이 감싼 구조다. 연결망 강조는 별도 기능 설계가 필요한데 라우터/지오메트리 작업에 밀려 있었다고 보는 것이 합리적이다 [추정].

## B. Screenshot Critique (영역별, 번호 주석)

기준: 1440×900, 100% 줌. 레이아웃 실측: 헤더 52px, 보조 툴바 36px, 좌 240px, 우 292px, 분석 도크 28px, 상태바 28px.

**① Header (52px)**
- `Circlith` 16px + 부제 9px, 프로젝트명 12px 굵게 + "메모리에서 편집 중" 10px. 가장 중요한 정보인 **저장 안 됨**이 가장 약하게 표시된다.
- `N committed edits`는 10px 영문이다. 한국어 UI에서 혼자 영어이고, 사용자 어휘가 아니다. 실제로 6개 부품 + 6개 배선 = "12 committed edits"처럼 편집 이력 길이일 뿐이다.
- 도구 분할 버튼: 선택된 `선택`은 흰 배경 + 그림자, 비선택은 `#f7f9fb`. 배경 대비 약 1.05:1이라 활성 상태가 약하다. 단축키 `v`, `w`는 소문자 10px 회색이다.
- Undo/Redo는 비활성 시 둘 다 연한 글자뿐이라 "존재는 하되 상태를 읽기 어렵다".
- 시뮬레이션 스위치 트랙(꺼짐 `#afbdc9`)은 흰 배경 대비 **1.92:1**로 비텍스트 3:1에 미달.

**② 보조 툴바 (36px)**
- `라이브러리 패널` / `Inspector`가 텍스트 링크처럼 보인다. 혼용 언어. 토글인지 상태인지 모호하다. `도면 01`은 클릭 불가 정적 라벨이다(시트가 하나뿐).
- 줌/맞춤/그리드는 헤더가 아닌 여기에 있다. 1024px에서 Inspector가 **오버레이로 열리면 우상단 줌 컨트롤이 가려진다** [실측].

**③ 좌측 사이드바 (240px)**
- 탭 "라이브러리/도면 트리" + 라벨 "라이브러리 검색" + 입력창 + **"검색 A" 버튼**(모달 검색을 여는 세 번째 검색 표면). `A`가 키 힌트인지 이름인지 모를 표기다.
- 9개 부품이 두 폴더(7 + 2)로 나뉜다. 폴더 헤더와 아이콘은 읽기 쉽고 아이콘 42×27px로 충분히 알아볼 수 있다. 부품 수 대비 폭 240px(15%)은 후하다.
- 하단 "조작 안내"는 `<details open>`으로 항상 펼쳐져 있다. "Pan: 프리셋 참조"는 사용자에게 의미 불명.

**④ 캔버스 (908×755, 화면의 52.9%)**
- 기본 100%에서 2입력 AND는 약 52×40px다. 빈 도면에는 **시작 안내가 캔버스 위에 전혀 없다**(안내는 Inspector에만). 첫 화면에서 시선은 캔버스 중앙 빈 면에서 갈 곳을 잃는다.
- 격자 점은 아주 옅다. 시뮬레이션 OFF에서는 배선 값 라벨이 없다.

**⑤ Inspector (292px)**
- 상단 `COMPONENT`(9px, 자간 1.4px, 청록)과 `XOR`(18px). 제목은 객체 이름이다. 종류 행은 이름과 같은 값을 반복한다(`XOR`/`XOR`).
- `입력 수`/`입력 반전` 행이 **Input/Output에도 표시**된다(Input: 입력 수 0, 반전 없음). 의미 없는 행이다.
- 핀 목록: `IN 1`, `OUT 3`처럼 번호가 입력·출력을 합쳐 센다. 2입력 XOR의 출력이 `OUT 3`이다. 캔버스는 `I0`, `I1`, `O`로 쓴다. 번호 체계가 세 곳(캔버스/Inspector/툴팁)에서 다르다. 연결망은 "연결망 4"인데 배선 선택 시에는 **UUID 원문**이 나온다(`3d2999af-a72f-…`).

**⑥ 상태바 (28px, 10px)**
- 한 줄에 `SELECT | 선택 N | 입력 대기 | [메시지 · Undo힌트 · Redo힌트 · 프로파일 · 입력 대기] | 100% · Grid 10 | Logic OFF`. `입력 대기`가 **두 번**(세 번째 세그먼트와 긴 문자열 꼬리) 나온다.
- 초기 안내("왼쪽 부품을 도면으로 드래그하세요…")는 부품 6개를 놓은 뒤에도 남는다 [실측]. 배선 후 "연결했습니다. 점은 접속점이며…" 설명문이 상태로 남는다. 상태와 튜토리얼이 섞인다.
- 1024px 이하에서 메시지가 잘린다 [실측, 가시폭 690px→520px].

**⑦ 심벌**
- 게이트 형태는 일관적이다(AND 곡선, OR/XOR 이중 곡선, 버블). 선택 윤곽은 점선 사각형이다.
- Input/Output 본체는 26×11px 작은 오각형이며 값 글자는 **6px**이다. 핀 이름 `I0/I1/O`는 **7px**이다. 줌 72%(100개 맞춤)에서는 사실상 장식이다.
- 두 Input이 모두 `Input`으로 표시되고 패널 쪽은 `Input 1/2`다. 어느 것이 1번인지 캔버스에서 알 수 없다.

**⑧ 배선**
- 2px 선, 접속 핀 3.6px 점, 핀 히트 영역 10px. 접속점 점(`r=4`)은 `/zoom`로 크기가 일정하다.
- **서로 다른 연결망 겹침(F01)** — 본 감사의 최대 문제.
- 시뮬레이션 색: 0 `#3a6379`(일반 배선 `#346a7a`와 대비 1.08:1, 거의 같은 색), 1 초록, X 빨강 점선, Z 보라 점선. 0 vs 비활성은 라벨로만 구분된다. X/Z는 점선 패턴 중복 부호화가 있어 색각 이상에 대비했다(이 부분은 잘 설계됨).

## C. Nielsen 휴리스틱 평가

| # | 원칙 | 위반/근거 |
|---|---|---|
| 1 | 시스템 상태 가시성 | 저장 상태가 10px 회색(F02). 상태바 메시지가 오래 남음(F11). 시뮬 출력이 접힘선 아래(F05). 반면 도구/선택/줌/Logic 표시는 충분하다. |

| 4 | 일관성/표준 | 부품 이름 3종, 핀 번호 3종, 폰트 11종 크기, 포커스링 2종(F13). Inspector가 이름·종류를 반복. |

| 6 | 기억보다 인식 | 단축키가 버튼에 병기됨(좋음). 그러나 `검색 A`, `Shift+Space`, `프리셋 참조`는 기억을 요구. 캔버스에 시작 안내 없음. |
| 7 | 효율성/유연성 | 가속 키는 풍부. 반복 배치는 부품당 2클릭(F09). 다중 선택 시 정렬·일괄 속성 없음. |
| 8 | 미니멀 디자인 | Inspector 하단 버튼/카드/디버그 문구, 좌측 조작 안내 + 개발자 메모, 3중 중복 정보(F04, F07). |
| 9 | 오류 인식/복구 | 시뮬 진단은 있음(`관련 위치 보기`). 하지만 진단 대상에 배선 겹침이 없다. 진단 목록은 Inspector 하단·분석 도크에 중복. |
| 10 | 도움말/문서 | 도움말이 3곳에 분산(좌 조작 안내, Inspector `배선 조작법`, 상태바). 내용이 서로 다르고 점검 순서가 없다. |

| **Proteus** | 시뮬레이션 전용 계측기, 실행 중 상태 오버레이. | 아날로그 계측기는 범위 밖. | 출력이 우측 패널 숫자 배지뿐. 도면 위 Output 값은 6px. |
| **EasyEDA Pro** | 웹 CAD, 부품 검색 + 필터, 도킹 패널. | 클라우드 라이브러리 전제. | 검색이 3곳이지만 필터·즐겨찾기·최근 사용 없음. |
| **Logisim Evolution** | **속성 표가 항상 하단 고정**, 입력 핀을 캔버스에서 바로 클릭 토글, 부품 트리. 교육용 목적과 가장 가까움. | 시각 디자인은 낡음. | Circlith의 캔버스 직접 토글은 동일(+). 속성 직접 편집은 열세. |
| **CircuitVerse** | 도면 중심, **얇은 상단 + 접히는 부품 패널**, 시뮬 상태가 즉시 도면에 표시. | 대형 회로·정밀 편집은 약함. | Circlith는 크롬이 더 두껍다(캔버스 53% vs 대개 70%+ [추정]). |
| **Falstad** | 도면 위 **전압/전류를 색과 애니메이션으로** 직접 표시. | 아날로그 전용. | Circlith도 배선 색 + 값 라벨이 있다(+). 단 라벨 12px, 한 선분당 하나뿐. |
| **NI Multisim** | 계측기 패널이 분리되어 결과를 고정 표시. | 무겁다. | 시뮬 결과가 선택 객체 아래로 밀리는 구조는 반대 방향. |

결론: Circlith는 Logisim/CircuitVerse **급의 교육용 도구가 목표라면** 크롬을 줄이는 쪽이, 전문 CAD 급이라면 **Inspector 직접 편집 + 네트 하이라이트**가 필수다. 현재는 두 방향의 부담(전문 CAD식 패널 + 교육용 수준의 기능)만 가진 어중간한 위치다.

## E. Workflow Friction (시나리오 측정)

모든 수치는 Playwright 자동화 실측이며 **사람의 시간이 아니다.** 클릭 수·포인터 이동은 사람의 조작 비용 근사치로 쓸 수 있다. 라이브러리 클릭 시의 포인터 이동은 추적에서 제외되어 실제는 더 길다.

| 시나리오 | 결과 |
|---|---|
| **A 초보자** (Input×2, AND×2, Output×2 배치 + 6배선) | **24클릭, 키보드 0, 캔버스 포인터 경로 ≈ 4,640px.** 배치 12클릭(부품당 라이브러리 클릭 + 캔버스 클릭), 배선 12클릭(핀-핀 2클릭씩, 배선 도구 전환 불필요 — 핀 클릭이 곧 배선 시작: 좋음). 빈 캔버스에 안내 없음. 마지막에 **연결망 겹침(F01)**이 생겼는데 어떤 경고도 없었다. |
| **B 반복** (게이트 10개) | 20클릭. 실측 100개: 200클릭. 각 배치 평균 73ms(처음 10개 58ms → 마지막 10개 93ms, +60%)로 배치 연산 자체는 부하가 점진적으로 늘지만 체감 문제는 아님. **연속 배치 모드는 확인하지 못함**(미검증). |
| **C 속성 변경** (4입력 XOR + 입력 2 반전 + 이름 변경) | **4클릭 + 텍스트 입력 2회**: 선택 1, `속성 편집…` 1, 반전 체크 1, `적용` 1. 모달이 도면을 가림. 이름은 Inspector에서 직접 못 바꾼다. 모달은 13~16px 글자로 Inspector(10~11px)와 크기 체계가 다르다. 적용 후 Inspector는 `OUT 5`(4입력 XOR의 출력). |
| **D 오류 복구** | 배선 클릭 → 선택되면 Inspector가 `WIRE / NET`, UUID 노출. 삭제는 `Delete`, 복구는 `Ctrl+Z`. 기능은 동작하지만 **잘못 겹친 배선은 "오류"로 인식되지 않으므로 복구 동기가 생기지 않는다.** |
| **E 시뮬레이션** | 캔버스의 Input 클릭 1회로 토글(좋음). 두 Input을 1로 만들면 출력 1/1. Input 1을 X로 바꾸면 해당 배선과 출력이 **빨강 점선 `X`**. 문제: 출력 `Output 1/2`는 우측 패널 하단이라 **선택된 객체의 Inspector 아래로 밀리고**(900px에서 출력 y≈800–840, 진단 제목이 접힘선에 걸림) 캔버스의 Output 값은 6px. 캔버스는 `Input`/`Input`, 패널은 `Input 1`/`Input 2`. |
| **F 대형** (100 게이트) | 줌 72%에서 전체 맞춤 가능. 유휴 91프레임/1.5s(≈61fps), 휠 줌 15단계 632ms(≈42ms/단계, 헤드리스), 전체 선택 31ms. **도면 트리는 100행 비가상화, 높이 4,322px**(화면 820px의 5.3배). 행마다 종류 태그와 이름이 중복(`AND` `AND 1`). 다중 선택 Inspector는 "좁히세요" 안내 + `선택 항목 화면 맞춤`뿐. 배선 100+는 미측정. |
| **G 작은 화면** (1024×768) | 캔버스 **64%**. 좌 패널은 216px 고정 점유, Inspector는 **캔버스 위 오버레이**(290px)로 열려 줌/맞춤/그리드를 가린다. 상태바 메시지 잘림. 960×600에서는 두 패널을 열면 530/960px(55%)를 덮는다. 가로 스크롤은 390px까지 없음. 패널 초기 열림 여부는 **마운트 시점 `window.innerWidth`로 한 번만** 결정되고(`App.tsx:117–118`) 이후 크기 변경이나 재방문에 반응/저장하지 않는다. |

패널 점유율 [실측, 1440×900]: 캔버스 52.9%, 좌 15.2%, 우 18.5%, 헤더 5.8%, 보조 툴바 2.5%, 상태바 3.1%. 세로 크롬(52+36+28+28)은 144px(16%). 1280×800은 캔버스 50.4%.

## F. Visual Design Audit

### 타이포그래피 [실측 문자 수 기준, 시뮬 ON 화면]
| 크기 | 문자 수 비중 |
|---|---|
| 9–10px | 24% (헤더 부제, 상태바, eyebrow, kbd, 핀 보조) |
| 11px | 47% (Inspector 본문, 도움말, 도구 버튼) |
| 12px | 8% |
| 13px 이상 | 21% (모달, 라이브러리 이름, Inspector 제목 18px) |

- **11px 이하가 71%.** 11px는 100% 화면에서 읽기는 되지만, 본문·보조·경고가 **같은 크기**라 위계가 크기가 아니라 색(회색/청록)에만 의존한다.
- 정보 중요도와 크기가 불일치: `0 committed edits`(보조)와 `메모리에서 편집 중`(중요한 경고)이 둘 다 10px 회색. 반대로 Inspector 제목 `XOR` 18px와 `COMPONENT` 9px 사이는 위계가 뚜렷하다(잘된 부분).
- 사용된 폰트 크기: 7/9/10/11/12/13/14/16/18/21/22px — 11단계, 체계 없음.
- **일괄 확대는 해법이 아니다.** 키울 곳: 저장 상태, 시뮬 출력값, 도면 내 핀 라벨(최소 9–10px 화면 크기), Input/Output 값. 줄이거나 없앨 곳: 상태바 꼬리 문구, `committed edits`, 개발자 메모, 반복 도움말.

### 확대(125%/150%) [실측: 유효 뷰포트 1152×720, 960×600]
- 1152×720(125%): 헤더·툴바 깨짐 없음, 캔버스 64.9%, Inspector는 기본 닫힘(`<1200`)이고 열면 오버레이로 캔버스 위. 960×600(150%): 상태바 잘림, 헤더는 유지. **깨지지는 않으나 "작은 글자를 키우면 패널이 오버레이로 바뀌는" 방식으로 해결**한다. 확대는 읽기성을 개선하지만 편집 공간을 크게 줄인다.

## G. Information Architecture

| 패널 | 현재 책임 | 문제 | 있어야 할 책임 |
|---|---|---|---|
| 헤더 | 브랜드, 프로젝트, Undo/Redo, 도구, 편집 수, 시뮬 스위치, 설정 | 저장/파일 없음, 편집 수는 노이즈 | 파일 상태, 실행 취소, 도구, 모드 |
| 보조 툴바 | 패널 토글, 도면 라벨, 줌 | 헤더와 역할 경계 모호, 정적 라벨 | 뷰 컨트롤(캔버스에 붙이기) |
| 좌 패널 | 라이브러리 + 도면 트리 + 도움말 | 검색 3중, 도움말·개발자 메모, 두 목적(배치/탐색)을 탭으로 공유 | 부품 배치 / 도면 탐색(큰 회로에서) |
| Inspector | 5~6역할 | 아래 참조 | **선택 객체 속성 + 직접 편집** |
| 분석 도크 | 진단 목록(접힘) | 진단이 Inspector와 중복 | 진단/파형(향후) |
| 상태바 | 도구·선택·메시지·줌·Logic | 상태+도움말+튜토리얼 혼합 | 상태 + 일시 메시지만 |

Inspector 책임 분석 (**객체 정보 표시기이자 명령 패널이자 설정 패널**이다):
1. 객체 정보: 종류/입력 수/회전/입력 반전, 핀·연결·값 (읽기 전용)
2. 전역 설정: "스마트 자동 · 자동 우회" 카드 + `Shift+Space`, 드래그 중 `R` 안내
3. 중복 상태: "선택 N개 부품·M개 배선" (헤더·상태바에 이미)
4. 전역 통계: "연결망 N개 · 접속점 M개"
5. 명령 버튼: 연결 유지 이동, 회전 2종, 취소, 꺾임 전환, 경유점 제거, 선택 삭제, `선택 항목 화면 맞춤`, 배선 도구 6종(배선 선택 시)
6. 개발 흔적: `초안: NONE / 도구: SELECT`
7. 시뮬레이션 패널(모드 ON 시), 중복 정리 미리보기

권고 정보 구조:
- **아무것도 선택 안 함**: 회로 개요 요약(부품·연결망·진단 수) + 시작 안내 한 문단. 명령 버튼 없음.
- **단일 부품**: 이름(편집 가능), 종류(보조 텍스트), 입력 수 스테퍼, 입력별 반전 토글, 회전 버튼 2개, 핀 표(핀 이름·연결망 이름·값). `속성 편집…` 모달은 삭제.
- **배선**: 연결망 이름(UUID 금지), 양 끝, 값, `연결망 전체 선택`/`분기` 등 배선 도구 2~3개.
- **다중**: 종류별 개수, 공통 속성(회전·정렬), 정렬/분배, 일괄 삭제.
- 배선 설정(라우팅)·단축키 도움말은 설정/도움말 팝오버로 이동.
- 시뮬레이션 결과는 선택과 독립된 고정 영역(하단 도크 또는 우측 상단 고정 카드)에 둔다.

연결망 번호 "연결망 4"는 사용자에게 의미가 없다 [추정]. 그 번호가 가리키는 대상을 캔버스에서 찾을 방법도 없다. 이름/강조가 따라야 의미가 생긴다.

## H. Architectural Constraints

| `Editor`는 클래스 + `render` 카운터 강제 갱신 | `const [, render] = useState(0)`, `editor.*` 변경 후 수동 리렌더 | 반응형 UI 상태(선택·초안)와 문서 상태가 한 객체에 결합 |
| CSS 직계 자식 선택자 | `.properties > h2`, `.properties > button`, `.properties > p` | Inspector 내부를 컴포넌트로 옮기면 스타일이 깨짐 |
| 모달 상태 | `propertyComponent`(모달) + `inspectorOpen`(패널) 별도 | 직접 편집 도입 시 같은 값을 두 곳이 편집하게 되는 위험 |
| 속성 변경 경로 | `editor.updateProperties(id, {name, inputCount, invertedInputs})`는 원자적이며 오류 시 throw | **직접 편집으로의 전환은 쉽다** — 필드마다 같은 API를 호출하면 됨(commit-on-blur) |
| 반응형 패널 | 초기 열림이 `window.innerWidth` 1회 판정, 오버레이/그리드 전환은 CSS | 도킹 모드(고정/오버레이/숨김)를 상태로 모델링하지 않았다 |
| 레이아웃과 좌표 | 줌/팬은 `editor.viewport`, SVG는 컨테이너 100% | 패널 폭 변경이 회로 좌표를 깨는 증거는 못 찾음. 단 패널 토글 시 도면 재중심은 없음(미검증) |
| 가용 테스트 | `tests/browser/workspace.spec.ts` 존재(미커밋) | 개편 시 회귀 방어 가능성은 있음 |

리팩터링 난이도: Inspector 분리와 직접 편집은 **중간**, 네트 하이라이트는 렌더러에 `netByWire/netByPin` 인덱스가 이미 있어(`CircuitSvg.tsx`의 `connectedPins` 등) **낮음~중간**, 라우터 레인 분리는 **높음**.

## J. Prioritized Findings

> 심각도는 수정 난이도와 무관하다.

**F01 — 서로 다른 연결망의 배선 겹침**
- Severity: **Critical**
- Location: 라우터 결과(캔버스), `CircuitSvg.tsx` 렌더, 분석/진단
- Observed evidence [실측]: Input1·Input2 → AND 2개를 2입력 모두 연결하면 배선 `db9d`(Input1 net, `450,200→450,390`)와 `fada`(Input2 net, `450,400→450,210`)가 `x=450`, y 210~390에서 완전히 겹친다. 시뮬레이션에서 Input1=X, Input2=1일 때 같은 수직선에 초록 실선과 빨강 점선이 번갈아 보인다. `diagnostics`는 비어 있음. 연결망 수는 4개로 **논리는 올바르다.**
- Problem: 전기적으로는 분리된 두 연결망이 시각적으로는 하나의 버스/단락처럼 읽힌다.
- User impact: 회로를 읽는 사람이 단락을 의심하거나, 잘못된 회로로 오해한다. 교육용에서 치명적.
- Likely root cause: 라우터가 같은 연결망 내 우회/충돌만 고려하고, 다른 연결망과의 **동일 선상 중첩**은 검출/회피하지 않는다. 교차용 브리지는 수직·수평 교차만 처리.
- Recommended change: (1) 다른 연결망 배선의 동일 선상 중첩을 `wire-overlap` 진단으로 추가하고 주황 표시, (2) 자동 라우팅에서 레인 오프셋 적용, (3) 연결망 선택 시 같은 net 전체 강조.
- Alternative: 우선 (1)만으로 사용자에게 경고.
- Implementation effort: (1) 낮음, (2) 높음, (3) 낮음
- Regression risk: (1) 낮음, (2) 높음 — 기존 라우팅 스냅샷 테스트 영향
- Validation method: 2×2 회로를 만든 뒤 서로 다른 net의 선분 교집합 길이 0 단언(Playwright/단위), 겹침 시 진단 코드 존재

**F02 — 회로 저장/불러오기 및 이탈 경고 없음**
- Severity: **Critical** (제품 특성상 "데이터 손실")
- Location: `App.tsx`(저장 없음), 헤더 프로젝트명/상태
- Observed evidence [코드]: `localStorage` 사용은 입력 프로파일/라우팅/배선 표시 3종뿐. `beforeunload` 없음. 프로젝트명 `<input defaultValue="Untitled circuit">`는 비제어이며 어디에도 저장 안 됨. 상태 표시는 10px "메모리에서 편집 중".
- Problem: 새로고침·탭 닫기로 작업 전부 손실. 표시가 너무 약하고 입력 가능한 이름 필드가 저장 가능하다는 착각을 만든다.
- User impact: 100개 부품 회로를 만든 뒤 실수로 닫으면 복구 불가.

- Alternative: 저장 구현 전까지 헤더 배지 "저장되지 않음 · 새로고침 시 사라짐"(경고색).

- Regression risk: 낮음
- Validation method: 편집 후 새로고침 → 복원/경고 확인

**F07 — 부품/핀/연결망 명칭 불일치와 UUID 노출**
- Severity: **Medium-High**
- Location: `CircuitSvg.tsx`(라벨), `EditorSidebar.tsx`(트리), `InspectorPanel.tsx`
- Observed evidence [실측]: 같은 AND가 캔버스 `AND2`(이름==종류일 때 `종류+입력수`), 트리 `AND 1`, Inspector `AND`, 배선 Inspector `AND · OUT 3`. 2입력 XOR 출력이 `OUT 3`. 배선 선택 시 연결망이 UUID. 두 Input이 캔버스에서 둘 다 `Input`이고 패널은 `Input 1/2`.
- Problem: 객체를 가리키는 이름이 화면마다 다르다.
- User impact: 패널의 `Input 2`가 도면의 어느 것인지 알 수 없다.
- Likely root cause: 표시 이름을 화면별로 각각 계산.
- Recommended change: 단일 `displayName(component)` 함수(자동 번호 `IN1`, `AND1`, `OUT1`)를 모든 화면이 공유. 핀은 `A,B,Y` 또는 `I0,I1,O`로 통일. 연결망은 `N1…` 자동 이름 + 캔버스 강조.
- Alternative: 캔버스 라벨에 번호만 추가.
- Implementation effort: 낮음~중
